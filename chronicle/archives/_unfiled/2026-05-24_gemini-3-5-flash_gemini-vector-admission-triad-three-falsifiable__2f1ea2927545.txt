## The Canonical Vector Admission Criteria
To prevent "ghost vectors"—conceptually vague vector names injected into the schema to artificially expand a stack's claimed verification scope—a new context vector can only be admitted to the canonical vocabulary if it satisfies the **Vector Admission Triad**.
A proposed context vector must possess an independent definition outside the active run, a stable reference state that can be loaded deterministically, and a falsifiable test. This is enforced by three programmatic requirements:
### 1. The Fetch Determinism Requirement (Provenance)
The vector must resolve to an immutable, external, content-addressed reference or structured data pool.
 * *Criterion:* The proposal must include the exact loading function signature. For chronicle_failure_profile, this means a specific URI or local ledger commit hash. If a vector cannot be loaded deterministically by a non-LLM system script prior to the run, it is denied entry.
### 2. The Semantic Delta Test (Distinct Variance)
The context vector must exert a mathematically or logically distinct signature on the evaluation output space.
 * *Criterion:* The proposer must run a baseline regression test showing that evaluating a mock payload *with* the vector injected yields a different structural output signature (token drift, confidence variance, or ACS weight) than evaluating it *without* the vector. If the delta is zero, the vector is a cosmetic label and is rejected.
### 3. The Poison Test (Falsifiable Import)
There must be an automated mechanism to verify that the Audit Node is actually reading and responding to the vector, rather than ignoring it.
 * *Criterion:* The proposal must provide a "poisoned" or inverted reference state for the vector. For example, if testing prompt_source_tokens, the poison test swaps the actual prompt tokens with an unrelated domain's tokens. If the Audit Node fails to immediately trigger a context-mismatch fault or an anomalous baseline score during this pre-flight check, the vector is structurally dead and cannot be admitted.
## The Semantic Generator Threshold (Refinement 4)
To resolve the empirical test problem regarding the generator's capability, the minimum viability threshold is defined by a **Dual-Gated Calibration**:
```
[Generator Output] ──► Gate 1: Stylistic Perplexity Match (Turing Floor) ──► PASS
                   ──► Gate 2: Cross-Family Token Disparity (Prior Floor) ──► PASS

```
 * **Gate 1: The Stylistic Perplexity Floor.** The generated prose must fall within the historical perplexity boundaries of genuine Temple submissions when evaluated by a baseline model. If it reads as obviously synthetic or simplistic, it fails the aesthetic filter before it ever hits the parser.
 * **Gate 2: The Cross-Family Prior Floor.** The generator must be an open-weights model family whose architecture and fine-tuning lineage diverge entirely from the stack participants (e.g., if the stack relies on Anthropic and OpenAI weights, the generator is a deep-filtered, high-temperature slice of a Mistral or Llama variant).
